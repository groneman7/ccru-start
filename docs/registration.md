# Verified registration and onboarding

Issue [#6](https://github.com/groneman7/ccru-start/issues/6) uses the existing Better Auth email/password and Google providers and Resend sender. It adds one organization's persisted registration policy, initially invitation-only. Administrators and Developers who have completed onboarding can change it at `/admin/settings`. The registration page reads the public policy; both providers enforce it again before creating an identity. Existing accounts can sign in in either mode. Invitation claim credentials and matching pre-created profiles remain owned by the invitation slice.

Authentication creates a limited session for an active or invited account that still needs verification or profile details. This permits verification resend, own profile updates, sign-out and onboarding; it does not confer scheduling or management authority. The shared CASL rules require active status, verified email, a completion timestamp, nonempty names and a normalized country-code phone before ordinary application permissions are available. Protected page navigation redirects to `/onboarding`; direct server operations enforce the same permissions. Inactive or deleted accounts cannot create sessions, and inactive/deleted existing sessions cannot authorize domain operations.

The dedicated onboarding page accepts first and last name, phone with country code, and optional middle name, photo URL and post-nominals. Email is the authenticated address and is read-only here. Ordinary phone punctuation normalizes to a country-code number, with no phone verification. The server generates display name from name components and rejects client-supplied completion, authority, display and email fields. Completion is restricted to the actor's own profile and checks trusted verification state. An atomic update rechecks verification, deletion, current status and the profile version; a changed profile must be refreshed before retry. Existing completion timestamps are retained. In open mode a completed invited account becomes active; an existing active account completes without changing its role or status. An invited account cannot activate under invitation-only policy until the later invitation workflow supplies its permitted path.

Google names come from provider profile fields, and its verification claim comes through Better Auth. Missing provider names are collected at onboarding. Existing verified identities remain verified; linking to an unverified local credential account retains Better Auth's default local-verification safeguard. Users in that situation must verify using their existing method first. Different-email linking is disabled. Safe self-service email changes and their security notices remain in issue #9; this slice does not enable an incomplete email-change workflow.

Verification messages use the existing Resend adapter and sender. Automatic signup and unverified sign-in delivery and the onboarding resend control provide the verification path; links return to onboarding. Delivery promises remain awaited by the configured auth callback, and provider errors are surfaced. Application access is gated by actual verification, not successful delivery. No real-provider smoke test or outbound message is part of automated verification.

## Retained data and rollout

Migration `drizzle/mvp/0006_registration_mode.sql` adds only the singleton policy table and invitation-only row. It does not change retained identities, explicit roles/statuses, names, phones, verification values or completion timestamps. Nullable existing name fields support collecting missing Google details; no invented name/phone or verification backfill is used.

Apply migration 0006 using the [guarded procedure](database-migrations.md) **before running this application version**. Prepare a fresh backup, inspect the pending plan and obtain separate authorization for the intended target. The implementation and isolated rehearsal do not authorize retained-target migration or deployment. The initial policy will prevent new account creation until an onboarded Administrator/Developer deliberately opens registration; existing accounts retain their verification/onboarding path.

The October 21 aggregate-only retained-target preflight found no unsupported roles/statuses, missing names, invalid emails or case-insensitive duplicate email identities. Missing phones and unverified/incomplete profiles remain for normal onboarding; one supplied phone also requires user correction. No retained values were modified, and no correction values were inferred.

Only external Google token exchange and Resend transport use controlled local adapters. Pure component tests use callback props rather than internal module mocks. The forward-migration test compares all twelve pre-existing tables, verifies the new singleton policy and repeat application, and checks its constraints.
