# Scheduling MVP specification

Publication status: published as [GitHub issue #2](https://github.com/groneman7/ccru-start/issues/2) with `ready-for-agent`; the product owner confirmed the testing seams on October 18, 2026.

## Problem Statement

Volunteers need to find events, understand position requirements, request a place, and handle withdrawals without losing track of their responsibilities. Staff need to manage limited capacity, qualifications, exceptional assignments, replacement requests, and understaffing consistently. The current application provides parts of event, template, assignment, and user management, but does not implement the approved scheduling lifecycle and supporting identity, authorization, review, notification, and recovery workflows.

The organization needs one scheduling website for multiple clinic locations and kinds of events. Staffing decisions must remain consistent under concurrent requests, staff permissions must be enforced on the server, and public/volunteer views must disclose only their permitted information. The MVP contains no patient data.

## Solution

Implement the scheduling MVP and supporting management workflows from the product-owner-approved October 18, 2026 design. Volunteers can join eligible vacant seats, submit conflicting ordinary requests for scheduler review, see their own pending assignments, and arrange late-withdrawal replacements. Schedulers can manage positions, events, shifts, templates, assignments, conflicts, withdrawals, cancellation, and understaffing. User managers can manage profiles, invitations, certifications, and user types. Administrators control Officer capabilities, ordinary role changes, and registration mode; Developers additionally control Developer roles and exceptional restoration.

Use the approved domain vocabulary and preserve the boundaries between opt-in conflict detection, targeted automatic pending resolution, and quiet Developer restoration. Retain domain records through soft deletion/deactivation, while keeping current assignment state rather than introducing a full ownership history.

## Implementation Decisions

1. **Authority and vocabulary.** The approved design governs business behavior and supersedes earlier interview material. Use Event, Position, Shift, Slot, Template, Scheduler, User manager, Upcoming, Active-capacity slot, Monthly participation, Assignment priority, and Suppression with their glossary meanings. Technical proposals can be refined without changing business rules. Follow the three existing architecture decisions: separate conflict detection from resolution; retain current assignment state; restore quietly.

2. **Application boundaries.** Extend the existing TanStack Start/React website, server-function/service/repository structure, Better Auth, Drizzle, and PostgreSQL rather than replacing the stack. Modify calendar, users, authorization, authentication/onboarding, and their UI/read models; add settings, invitations, user certifications, saved locations, notifications/reviews, alert reconciliation, and restoration responsibilities. Existing junction-table names need not change solely to match domain vocabulary. Centralize each domain command rather than maintaining bypass mutations with different checks.

3. **Server authority.** Resolve the actor from the trusted session and enforce authorization on every operation and response projection. Client actor IDs, roles, grants, ownership fields, or onboarding-completion claims do not establish authority. Cover framework server functions, loaders, and Better Auth/plugin endpoints, not only route/button guards. Replace currently broad Officer/admin-plugin access with the approved boundaries.

4. **Role/capability contract.** Each user has exactly one hierarchical role, User < Officer < Administrator < Developer. Officers can independently receive two organization-wide capabilities: scheduling management and user management. Users cannot receive them; Officers cannot delegate them. Administrator/Developer roles effectively have both. Every Officer can view full profiles and manage saved locations independently of grants. Administrators manage ordinary roles and Officer grants; only Developers grant Developer or change an existing Developer's role. Restoration is Developer-only. Certifications and user types never confer platform permissions; user type never affects eligibility. Authorization rules remain source-code behavior, without an MVP rules editor.

5. **Settings/time.** Use America/New_York for event interpretation and calendar boundaries. Monthly event limit defaults to 3 and late-withdrawal window to 72 hours; schedulers can change both organization-wide. Registration initially uses invitation-only mode; Administrator/Developer can switch to open. Do not add a configurable timezone workflow. Required event/template end is strictly after start on the same local calendar date. Upcoming means start strictly later than operation time; in progress includes start and excludes end; past begins at end.

6. **Identity and onboarding.** Support only email/password and Google through Better Auth. Open registration becomes active on verified email plus completed onboarding, without approval. First/last name, email, and phone with country code are required; middle name, photo, and post-nominals are optional. Generate display name from first, optional middle, and last name. Accept ordinary phone formatting and store a normalized number; phone verification is unnecessary. Own basic profile editing is allowed; user type mutation requires user management. Pending email change retains the existing verified sign-in identity until the new address is verified. Send verification to the new address and a security notice to the old address; no operational in-app email-change message. Review account linking against matching verified identity rather than treating the current permissive configuration as approved behavior.

7. **Profiles/invitations.** A user manager creates a profile, then optionally sends an invitation. Require first/last names and email for invitation, allow optional middle name, and permit the volunteer to supply phone at onboarding. Invitations never expire in MVP. Resend invalidates the previous link; revoke prevents claiming through that invitation but retains profile/assignments. Verified matching email is case-insensitive and either provider claims the same profile without duplication. Claim/resend/revoke are atomic: the first completion determines subsequent valid operations, and claimed profiles use normal account management. Invitation-only mode blocks uninvited account creation through both providers. Open registration may claim the existing matching profile despite a revoked invitation, but revoked credentials remain unusable. Switching to open leaves outstanding invitations valid. Invited profiles have no volunteer scheduling access before activation, but schedulers may assign them. Inactive users are never assignable. Bulk creation uses a multi-row form with independent success/errors; existing profile emails fail rather than update/reinvite implicitly. Invitation and authentication email delivery are required independently of in-app operational notifications.

8. **Deactivation.** Reject deactivation while upcoming non-deleted confirmed/pending/available assignments exist. Remove those assignments first; cancellation also removes them from active capacity. Successful deactivation revokes existing sessions immediately and blocks sign-in and new assignments. Preserve the profile and relationships. Do not conflate lifecycle state, email verification, and onboarding completion.

9. **Certifications.** Extend the hierarchical catalog with a separate user-certification relation and pending/verified/rejected state. Volunteer submission is pending; manager creation or approval is verified. Reject with optional reviewer comment, retain the rejected record, and notify the volunteer. A rejected submission can be edited/resubmitted on the same record. A volunteer can edit their pending submission without changing state or withdraw it through soft deletion; only user managers remove verified certifications. Renames preserve identity and verification. Approval has no certification-approval notification, though resulting assignment confirmation does. No certification dates/expiration are included.

10. **Eligibility.** Positions own the only eligibility expressions. Support arbitrary nested AND/OR over exact or descendant-inclusive verified certification predicates and hierarchical minimum-role predicates. No expression permits otherwise assignable active users, with the invited-user scheduling exception retained. Validate the expression language and references server-side; preserve branch alternatives in unmet-requirement explanations. Share one behavior across signup, scheduler assignment, replacement, requested rechecks, and automatic resolution. A versioned expression tree is a technical proposal rather than a newly approved business rule. Exclude NOT, exact-role predicates, user-type predicates, other eligibility dimensions, and event/template alternatives.

11. **Slot state and retention.** Confirmed, pending, and available occupy capacity and count for monthly participation. Rejected, cancelled, and soft-deleted slots do neither. Available retains its incumbent until released/replaced. Pending is an assignment reserving a seat, never a waitlist. Retain current owner/state and latest transition comment/actor/time, not full transitions or ownership history. A transition without a new comment clears the prior comment. Manual comments are optional on the server. Suppression approves all current conflicts as one decision; do not persist conflict lists, suppressed identifiers, or suppression history. Generate explanatory system comments for confirmed-to-pending rechecks and automatic confirmation. Deliver decision comments through notifications rather than event signup UI.

12. **Ordinary requests and scheduler assignments.** Before start, an active volunteer requesting a vacant seat passes all checks into confirmed; failed eligibility/monthly checks explain reasons and allow pending submission. Another active-capacity slot in that event hard-blocks an end-user request. Full shifts with no available replacement block further requests, including pending requests. Scheduler assignment/move without conflicts confirms; with conflicts, show reasons and permit suppress-all into confirmed or unsuppressed pending. Schedulers approve/reject pending with optional comment and volunteer notification; rejection releases capacity and retains the record. Retry creates a new slot without restriction. Scheduler assignment of invited profiles is allowed. End users cannot atomically change positions: withdrawal and a new request each follow their own rules.

13. **Shift/capacity/moves.** Enforce at most one non-deleted shift per event/position and one non-deleted template-position association per template/position. Capacity is a positive integer; removal represents zero. Reject reductions below active-capacity occupancy on the server and in UI. Scheduler assignment beyond capacity increases maximum by one with the assignment. Implement scheduler drag/drop through the same authoritative command, atomically moving/checking/suppressing/adjusting destination capacity. Same-event position moves preserve assignment timestamp; moves to another event start a new one. Do not leave the current unawaited/non-transactional capacity expansion behavior in place.

14. **Monthly participation and priority.** Count each distinct event with at least one remaining active-capacity assignment once, in the America/New_York calendar month of event start, including past events in that month. Exclude cancelled/deleted events and rejected/cancelled/deleted slots. Rank event participation by the earliest assignment-creation timestamp among that volunteer's remaining active-capacity slots in that event, never confirmation time. Warn only beyond the first N participations. Do not double-count the candidate's existing slot/event. Removing the earliest slot may change an event's rank. Replacement starts a new timestamp for the new owner and releases the incumbent's participation only if no other active-capacity slot remains in that event. A December replacement for a January event affects January participation. Overlapping event times are not a conflict rule.

15. **Withdrawals and replacements.** End-user slot actions stop at start. End users cannot change pending slots at any time; show generic contact-schedulers instructions without a new contact workflow/email setting. Confirmed withdrawal outside the configured late window soft-deletes immediately; inside it, retain the incumbent and set available. Available remains occupied/takeable with incumbent visible and can remain unresolved after start. Scheduler release soft-deletes without a volunteer notification solely for approval without replacement. Denial restores confirmed and notifies the incumbent with optional comment. End-user replacements must pass all checks and cannot become pending; scheduler replacements with conflicts require immediate suppression. Replace by updating the same slot's owner to confirmed with new assignment timestamp and latest replacement comment; atomically release and notify the incumbent and confirm the replacement through the ordinary confirmation path. Do not create a candidate record or extra seat. Once released into a vacancy, ordinary pending signup rules apply. Schedulers continue managing after start and in past events.

16. **Explicit conflict detection.** Relevant edits offer scoped rechecks with default OFF. Without an explicit request, do not scan existing assignments, preview/count conflicts, or generate scan notifications. New assignment/replacement checks still always run. Default scopes are that user's upcoming slots for user role/certification edits; upcoming slots for the edited position; that event's slots if its new start is upcoming; affected calendar months for monthly-limit changes. Schedulers may explicitly request all upcoming slots. A user manager may request the edited user's scoped check without scheduling capability and without gaining manual slot powers. Exclude slots once start is reached. Current conflicts make confirmed slots pending even after earlier suppression; failing pending stays pending. Available stays available with a generic scheduler review warning retaining requester/time but no conflict details. Viewing a warning does not scan; explicit recheck supplies reasons. Suppression clears it until a later requested check. Confirmed-to-pending updates own pending state and scheduler review without a volunteer notification.

17. **Targeted automatic resolution.** When blockers disappear, automatically reconsider affected upcoming pending slots, including certification approval, qualifying role change, participation removal, relaxed requirements, and increased monthly limit. Confirm only when all checks pass and the event ranks within the first N participations; earlier pending participation retains priority while missing another requirement. With A/B/C/D requested in order and limit 3, B's certification approval can confirm B while D stays pending. Scheduler-approved over-limit confirmed slots stay confirmed and do not take priority from earlier pending events. Resolution never demotes confirmed slots, performs a global detection scan, or decides withdrawal requests. Scope to affected users/positions/events/months and pending slots; available remains available. Generate a system explanation and one confirmation on automatic confirmation. No closure-time cleanup exists.

18. **Events/templates/locations.** New events publish immediately. Schedulers can edit past events indefinitely, including assignments, and history shows current related names/types rather than snapshots. Date/time/location changes notify assigned volunteers; title/description edits do not. Template creation copies details, positive-duration time values, location, positions/capacities, and thresholds to one event on a selected date. Template edits/deletion never propagate; created future events do not block template deletion; a source-template ID is optional provenance only. Saved-location autofill copies name/address into editable event/template values; edits never propagate. Every Officer can manage saved locations. Event type names/templates suffice without a managed taxonomy.

19. **Cancellation/deletion.** Cancellation is irreversible. Atomically cancel all active-capacity slots, retaining them while removing capacity/monthly participation, and notify affected volunteers with standard text plus optional custom message. Hide cancellation from public/ordinary volunteer calendars; retain access for affected volunteers via notification/history and for schedulers in all scheduling views. Schedulers may then soft-delete the cancelled event. Active-capacity slots block event deletion; resolve them through removal/cancellation first. Rejected/cancelled/deleted slots do not block. Permitted event deletion soft-deletes descendants and never physically removes domain records. Shift removal may soft-delete active slots and notify their volunteers with an optional custom message.

20. **Audience projections.** Public listing includes non-deleted, non-cancelled upcoming/in-progress events until exactly end, with title/name, date, time, location, description only. Exclude positions, capacities, vacancy counts, names, assignments, profiles, and public past-event access from server responses. Active volunteers see upcoming events regardless of certification, roster names, their own pending status, available slots/incumbents, and only their assigned past events including cancellations. Other volunteers' pending/review/conflict indicators are scheduler-only; roster access never grants full profile access. Every Officer may view full contact/certification profile details regardless of mutation grant. Schedulers see all scheduling/history including cancellations and review/conflict information. Signup/rechecks stop at start even though public visibility continues until end.

21. **Notifications and queues.** Operational delivery is in-app only. Use shared scheduling items for effective schedulers and shared pending-certification items for effective user managers, without claiming/assignment to one staff member. Keep per-recipient read/dismiss state distinct from global underlying resolution. Withdrawing a pending certification resolves its item; editing keeps the same item current. Replacing/releasing/suppressing an available slot resolves its incumbent warning; an unresolved warning remains visible after start. Retain delivered message text independently of latest comments/review updates. New or recurring actionable conditions may create/reopen items under their lifecycle rules. Comments and notifications use soft deletion where applicable, with latest slot-comment replacement exempt from complete history retention.

22. **Notification delivery contract.** Apply the following matrix, avoiding duplicate confirmations from overlapping triggers:

    | Trigger                                                     | Audience/behavior                                                     |
    | ----------------------------------------------------------- | --------------------------------------------------------------------- |
    | Pending slot, requested review conflict, withdrawal request | Shared scheduling queue                                               |
    | Pending certification                                       | Shared user-management queue                                          |
    | Slot approval/rejection                                     | Volunteer, optional reviewer comment                                  |
    | Automatic assignment confirmation                           | Volunteer, generated explanation                                      |
    | Certification rejection                                     | Volunteer, optional reviewer comment                                  |
    | Certification approval                                      | No certification-approval notification                                |
    | Requested confirmed-to-pending recheck                      | Scheduler review and own pending indicator; no volunteer notification |
    | Late withdrawal approval without replacement                | No volunteer notification                                             |
    | Late withdrawal denial                                      | Incumbent volunteer, optional comment                                 |
    | Successful replacement                                      | Released incumbent plus one ordinary confirmation for replacement     |
    | Scheduler assignment/reassignment/removal                   | Affected volunteer(s), optional comment                               |
    | Entire shift removal                                        | Active-slot volunteers, optional custom message                       |
    | Event date/time/location change                             | Assigned volunteers                                                   |
    | Event title/description edit                                | No notification                                                       |
    | Event cancellation                                          | Active-slot volunteers, standard text plus optional custom message    |
    | Confirmed self-signup                                       | One in-app confirmation                                               |
    | Immediate self-withdrawal                                   | On-screen success without another in-app notification                 |
    | Pending self-signup                                         | Pending status plus existing shared review item                       |

23. **Understaffing.** Allow zero or multiple thresholds per event shift/template position; template thresholds copy at creation. Use fixed Warning/amber and Critical/red severity with days/hours lead time relative to event start. Understaffing means occupancy below full maximum, not a separate minimum-filled target. Confirmed/pending/available count as filled. Show one current alert per shift at highest unresolved severity and expose lower thresholds in details. Manual resolution is threshold-specific; a new reached threshold creates new urgency. Filling, cancellation/deletion, or event end resolves alerts; filling then renewed vacancy while a threshold remains active reopens an alert. Personal dismissal is not global resolution. Choose a supported server reconciliation/job mechanism during implementation that runs without edits or page visits; client-only coloring is insufficient. The job technology is not a product decision fixed by this spec.

24. **Soft-deletion restrictions.** Retain users, catalog records, templates, events, shifts, slots, notifications, and comments through soft deletion/deactivation where appropriate. Exclude deleted records from normal views and preserve permitted retained relationships in history. Block Position deletion for future-event or template references, but not past-event references alone. Block certification catalog deletion for non-deleted user assignments, child certifications, or expression references. Block user type deletion while assigned to any non-deleted profile. Retained deleted references do not block certification/user-type deletion; later link restoration validates current conditions. Template-created events do not block template deletion. Apply domain checks rather than blanket rejection for all foreign-key references. Audit current physical-delete paths and cascading schema declarations. Revoked/expired sessions and one-use verification/reset tokens may be physically removed; retention must not preserve usable revoked credentials.

25. **Quiet restoration.** Only Developers restore. Preserve original business data, assignment timestamps, latest metadata, and slot states, including pending/available/confirmed; restoration is not signup. Suppress monthly-limit, eligibility, and duplicate-event conflicts for standalone slot/shift/event restoration without persisting conflicts or suppression history. Reject structural failures atomically: duplicate live shift/position associations, insufficient capacity, inactive users, and active assignments under cancelled/still-deleted parents. Event restoration cannot partially succeed and restores only descendants deleted in its root cascade, leaving independently deleted descendants alone. A cancelled event remains cancelled with cancelled slot states. Deletion-operation provenance is a proposed implementation technique. Restoration creates no volunteer/staff/review notifications, does no rechecks or automatic confirmations, retains existing review states, and does not redeliver old messages. Do not demote/flag/notify other assignments newly beyond limits; later ordinary signup/replacement evaluation includes restored participation and explicit recheck may flag it. Ordinary scheduled understaffing reconciliation resumes normally.

26. **Data/concurrency contract.** Add the required lifecycle/deletion metadata, Officer grants, organization settings, user-certification verification, global eligibility expressions, assignment timestamps/latest transition metadata, saved locations, invitation claim state, threshold definitions, notification/review items, and recipient states. Keep state/deletion orthogonal where useful. Schema shape remains an implementation choice subject to these contracts. Use transactions/concurrency control for seat reservation, monthly participation ordering, duplicate participation, replacement, moves, scheduler overflow, invitation claim/resend/revoke, cancellation, and restoration. Two simultaneous ordinary last-seat requests cannot overbook; competing replacements have one winner; stale drag/drop cannot overwrite a newer replacement. Commit assignment and any capacity expansion together. Recheck the current Neon HTTP database adapter's transaction capabilities before selecting the transaction implementation; preserve the existing stack while choosing a supported atomic mechanism.

27. **Conditional retained-data prerequisite.** This is schema evolution, not an assignment import feature. Before a migration that retains existing records, inspect the actual retained data. Map legacy active slots to confirmed and legacy deleted slots to soft-deleted; preserve users, identities, roles, explicit statuses, and relationships. Missing/ambiguous user status and missing event/template end require explicit review/correction. Do not infer verification for unexpected existing user-certification data. If retained assignments lack creation timestamps, settle an explicit repair/backfill policy before enabling dependent monthly enforcement. No common migration timestamp, UUID-derived priority, fallback order, or other timestamp policy is approved; slot creation time would not reliably establish the current owner's assignment time after replacements. The checked-in slot schema currently has no assignment timestamp; no live assignment rows were inspected for this spec. This conditional prerequisite blocks only affected retained-data work, not unrelated implementation. This spec does not authorize deployment or production migration.

## Testing Decisions

**Testing seams approved by the product owner on October 18, 2026:**

- **Primary seam: server operations.** Exercise the existing server-function command/query boundary with real session authorization and an isolated PostgreSQL test database. Drive calendar, users, grants/settings, certifications, invitations, review/notification reads, cancellation/deletion/restoration, and audience projections through the authoritative operations callers actually use. Extend the existing boundary instead of creating test-only entry points. Assert returned/persisted domain outcomes, permission denials, and visible messages; avoid mocks of repositories, transaction counts, internal helper calls, or exact implementation structure. DB fixtures establish scenarios without testing through repository methods.
- **Authentication boundary where required.** Test Better Auth's public handlers for email/password and Google onboarding/claim behavior, session revocation, plugin authorization, and email change. Replace only external provider/email delivery with controlled test adapters; exercise application identity/authorization and database state for real. Do not contact real volunteers or providers in tests. This additional boundary is necessary because auth/plugin endpoints can bypass ordinary domain server functions.
- **Small UI workflow checks.** Use focused browser/component checks for behavior that server assertions cannot establish: branch-preserving requirement explanations, own pending indicator and forbidden actions, bulk row feedback, replacement/incumbent rendering, copied form values, personal versus global dismissal, and drag/drop calling the authoritative move command. Keep workflow coverage selective rather than duplicating the complete server matrix through a browser.
- **Time-driven entry point.** Invoke the supported reconciliation entry point with a controllable clock and a test database, using the same domain commands/read models. Prove alerts change as time advances without a page visit/edit. Do not add a separate public test API or test scheduler internals.

**Prior art and setup.** The repository already declares Vitest, Testing Library, jsdom, and a test script, but inspection found no application test/spec files or dedicated Vitest configuration. The existing server-function/service/repository separation and query response schemas provide the application seams; there is no established test suite to imitate. Add only the minimal test harness needed for these behavior checks. Database tests require an isolated database compatible with application migrations; never run fixture writes or tests against production. Unit tests for the expression evaluator may supplement, but must not substitute for operation-level authorization, concurrency, or visibility coverage.

**Acceptance coverage:**

1. **Authorization bypass attempts:** test each role and both Officer grants through direct server operations and relevant auth/plugin endpoints. Officer without scheduling grant cannot mutate scheduling; every Officer can view full profiles/manage locations; user-management-only Officer can verify and request the user's recheck but cannot approve a slot. Users cannot hold Officer grants. Administrators cannot grant/demote Developer or restore. Client-supplied actor/role/ownership cannot establish authority. Return projections enforce the same audience boundaries as UI.
2. **Authentication and invitations:** both providers deny uninvited creation in invitation-only mode; case-insensitive verified email claims exactly one existing profile and retains assignments; wrong/unverified identity cannot claim. Check incomplete onboarding, required name/phone normalization and generated display name, active open registration, no access for unclaimed profiles, mode-switch validity, no invitation expiry, resend/revoke invalidation, open-mode claim after revocation, and concurrent claim/resend/revoke. Bulk valid rows persist independently of invalid/duplicate/existing-email rows. New email cannot sign in before verification, existing verified identity continues, and verification/security emails reach the correct test sinks.
3. **Deactivation:** upcoming confirmed/pending/available slots block deactivation; cancelled/deleted slots do not. Successful deactivation invalidates an existing session and prevents new sign-in/assignment, while invited profiles remain scheduler-assignable. Reject unauthorized profile/status/user-type changes.
4. **Certifications and expressions:** exercise pending edit/withdrawal, manager-created verification, rejection/resubmission on the same record, catalog rename preserving verification, verified-removal permissions, and queue lifecycle. Cover nested AND/OR alternatives, exact/descendant-inclusive certifications, minimum role hierarchy, no-expression positions, and user type having no effect. Reject invalid language/references server-side; verify certification approval has no standalone approval notification.
5. **Slot lifecycle/capacity:** eligible signup confirms; failed ordinary eligibility/monthly check allows pending and reserves capacity; duplicate-event end-user request/full shift blocks. Scheduler conflicted assignment supports suppression or pending; approval/rejection have expected capacity/messages, retained rejected records permit retry, comments are optional and later absent comment clears prior text. Server rejects nonpositive/fractional capacity, duplicate live event/template position associations, and capacity below occupancy. Two concurrent ordinary last-seat requests create at most one assignment; scheduler overflow atomically adds capacity. Same-event move preserves timestamp; another-event move replaces it. Stale move/replacement operations cannot overwrite newer ownership.
6. **Monthly ordering:** default fourth distinct event is pending; confirmed/pending/available count and multiple positions in an event count once; rejected/cancelled/deleted do not. Include past events in the start month; test month/year edges and America/New_York timezone/daylight-saving boundaries independently of host timezone. Do not double-count the candidate. Replacement uses event-start month and new owner timestamp; removing the earliest remaining slot updates event priority. With limit 3 and A/B/C/D order, approving B's certification confirms B while D stays pending. Scheduler-approved over-limit confirmed participation never demotes itself or displaces earlier pending priority. No cross-event overlap rule is introduced.
7. **Withdrawal/replacement boundaries:** use a controllable clock to cover before/at start and both sides of the configured withdrawal window. Pending slots are never self-editable. Immediate withdrawal soft-deletes with on-screen success only. Late withdrawal preserves owner/state/capacity as available; denial confirms with notification, release creates vacancy without approval notification. Failed volunteer replacement blocks rather than creating pending; scheduler conflicted replacement requires suppression. Concurrent replacement has one winner, keeps the slot identity and capacity, sets new owner timestamp, releases incumbent, and sends one replacement confirmation plus incumbent release notice. Scheduler operations remain available after start/past end.
8. **Detection versus resolution:** an edit without opt-in performs no detection scan, conflict preview/count, or scan notifications; targeted pending resolution still runs where prescribed. Explicit scopes skip started slots, demote conflicting confirmed to pending even after suppression, retain failing pending, and preserve available with generic warning/requester/time. Warning reads do not scan; explicit check returns current reasons; suppression clears the warning. No volunteer message for confirmed-to-pending. Certification/role/participation/requirements/limit improvements resolve only affected qualifying upcoming pending, never demote confirmed or decide available withdrawal. Past pending/available remain until scheduler action.
9. **Events/copies/cancellation:** events/templates require same-date positive duration, with no inferred missing end. Creation publishes immediately. Template and saved-location copies remain unchanged by later source edits/deletion. Date/time/location notify assigned users; title/description do not. Cancellation is irreversible, retains cancelled slots, frees monthly/capacity, and changes calendar/history visibility. Active-capacity assignments block event deletion; eligible deletion soft-deletes descendants. Past editing uses current related profile/position/user-type data without closure or snapshots.
10. **Privacy/time/history:** public payloads contain only approved event details and omit all staffing/profile fields, including vacancy counts. At start public visibility continues while signup/rechecks stop; at end public listing removes the event and assigned-history access applies. Volunteers see roster names, available incumbents, and only their own pending status; direct profile/history queries cannot reveal other users' restricted details or unrelated past events. Affected volunteers can follow cancellation notifications/history; schedulers retain all scheduling visibility.
11. **Queues/delivery:** assert the full delivery matrix, including intentional absences, using a fake delivery sink only at external email boundaries. Personal dismissal does not affect another recipient or globally resolve work; underlying resolution closes shared items. Pending certification edit retains its item; withdrawal resolves it. Available warning resolution follows replacement/release/suppression and remains actionable after start otherwise. Later transition-comment clearing/review updates never rewrite delivered text; automatic/signup/replacement confirmations are not duplicated.
12. **Understaffing clock behavior:** no thresholds required; copied multiple thresholds use fixed severities/day-hour lead times and full capacity including pending/available. Show one highest unresolved alert with lower details. Reconcile without edits/page visits; filling/cancellation/deletion/end resolves; renewed vacancy reopens while applicable. Manual resolution affects only its threshold, not a newly reached one; personal dismissal is independent.
13. **Deletion/restoration:** enforce each entity's domain restrictions using non-deleted references, retain permitted historical joins to deleted catalog records, and ensure no domain physical deletion. Developer-only root restoration restores only descendants from that cascade and rolls back entirely on structural failure. Standalone slot/shift/event restoration preserves timestamps/states and suppresses only the approved recoverable conflicts. Inactive users, duplicate live associations, insufficient capacity, and active assignments under cancelled/deleted parents reject. Cancelled events remain cancelled. Assert no new volunteer/staff/review notifications, rechecks, automatic confirmations, old-message redelivery, or automatic flags/demotion of other assignments, while later explicit checks and ordinary alert reconciliation still work.
14. **Retained-data migration:** use representative legacy fixtures to prove active/deleted slot mapping and identity/role/status/relationship preservation. Surface missing timestamps, ambiguous statuses, missing end times, or unexpected verification data for explicit repair decisions rather than inventing values. Do not claim the conditional prerequisite resolved without actual retained-data inspection and the needed approved policy.

## Out of Scope

- Inventory, clinic-flow management, patient/operational data collection, attendance tracking, and multiple organizations.
- Recurring event generation, draft publication workflow, managed event-type taxonomy, approval-based registration, CSV import, and an assignment-import feature.
- Additional authentication providers, phone verification, configurable organization timezone UI, granular Officer grants beyond the two approved capabilities, and a system-authorization rules editor.
- User type as permission/eligibility, additional eligibility predicates including NOT/exact-role, certification dates/expiration, event/template eligibility alternatives, and cross-event time-overlap conflicts.
- Waitlists, pending over-capacity end-user requests, pending replacement candidates, atomic end-user position switching, pending-slot self-edit/withdrawal, and end-user changes after start.
- Automatic global conflict detection on edits/reads, preview scans without request, persisted slot conflict/suppression lists, suppression analytics, complete slot transition/ownership/comment archives, and rewriting delivered messages from current state.
- Event closure/freezing/read-only deadlines, snapshots, attendance outcomes, close/extend/reopen flows, automatic closure cleanup, cross-midnight events, and cancellation reinstatement.
- Propagation of template/location edits into existing copied values, live template threshold linkage, user-customized alert severities/colors, separate minimum-filled targets, and in-app contact workflows.
- Operational email/SMS notifications; required invitation/authentication/email-change security emails remain included.
- Invented legacy timestamp/backfill priority, inferred missing statuses/end times/verification, production migrations, deployment, and sending real external messages as part of preparing this spec.
